# ADR-0001: Модульный монолит вместо набора микросервисов

- **Статус:** Accepted
- **Дата:** 2026-02-10
- **Автор:** Андрей К. (Tech Lead), согласовано с архитектором заказчика

## Контекст

Заказчик просит «микросервисы». При этом в команде 3 backend-разработчика, а корзина, цены,
заказ и оплата очень тесно связаны: один checkout затрагивает их все. Распределённые транзакции между
пятью сервисами на старте проекта обойдутся дороже, чем принесут пользы.

## Рассмотренные варианты

1. **Отдельный сервис на каждый домен** (cart, pricing, order, payment). Независимый деплой, но
   распределённые транзакции, сетевые задержки и пять пайплайнов для команды из трёх человек.
2. **Один сервис без внутренней структуры.** Быстро на старте, через полгода получится «big ball of mud».
3. **Модульный монолит.** Один деплой, пакеты верхнего уровня — модули с явными правилами зависимостей.
   При необходимости модуль можно выделить в отдельный сервис.

## Решение

Вариант 3. Правила:

- зависимости между модулями направлены в одну сторону, граф без циклов (см. ARCHITECTURE.md, раздел 2);
- модуль общается с другим модулем через его публичный сервис, а не через чужой репозиторий;
- JPA-сущности не выходят за пределы модуля и не попадают в HTTP-ответы;
- межмодульные реакции, которые не обязаны быть синхронными, реализуются через доменные события.

## Последствия

- Нужна дисциплина на ревью: компилятор не запрещает импортировать класс из чужого пакета.
  В бэклоге есть задача подключить ArchUnit или Spring Modulith, чтобы проверять правила тестом.
- Выделение модуля в отдельный сервис требует перехода с вызовов методов на API и с локальных
  событий на Kafka. Чем чище границы модулей, тем дешевле этот переход.
