# ADR-0003: Публикация событий заказа в Kafka

- **Статус:** Accepted (этап 1), Proposed (этап 2)
- **Дата:** 2026-06-15
- **Автор:** Андрей К. (Tech Lead)

## Контекст

Notification Service отправляет покупателю письма, Delivery Service создаёт отправления. Обоим нужны
события об изменении статуса заказа (SHOP-201). Классическая проблема **dual write**: нужно записать
изменение в PostgreSQL и отправить сообщение в Kafka, а общей транзакции у них нет.

Возможные сбои:

- сообщение отправлено, а транзакция БД откатилась: покупатель получает письмо о заказе, которого нет;
- транзакция закоммичена, а отправка не удалась: письмо потеряно.

Второй сбой для нас менее критичен, чем первый.

## Рассмотренные варианты

1. **`kafkaTemplate.send()` прямо в сервисе внутри транзакции.** Даёт первый сбой. Кроме того, связывает
   доменный модуль `order` с инфраструктурой.
2. **Доменное событие + `@TransactionalEventListener(phase = AFTER_COMMIT)`.** `order` публикует
   `ApplicationEvent`, `notification` отправляет его в Kafka только после коммита. Первый сбой исключён,
   второй возможен при падении процесса между коммитом и отправкой.
3. **Transactional Outbox.** Событие пишется в таблицу `outbox` в той же транзакции, отдельный
   процесс (поллер или Debezium) переносит записи в Kafka. Исключает оба сбоя, но добавляет
   инфраструктуру.

## Решение

- **Этап 1 (релиз 1.2):** вариант 2.
- **Этап 2 (после 1.3):** вариант 3, если потери событий станут заметны.

Общие требования к сообщениям:

- ключ сообщения — `orderId` (порядок событий одного заказа);
- у события есть `eventId` для дедупликации на стороне потребителей;
- значение сериализуется в JSON по контракту `docs/api/asyncapi.yaml`.

## Последствия

- `order` не зависит от Kafka, его можно тестировать без брокера.
- Слушатель с `AFTER_COMMIT` не сработает, если событие опубликовано вне транзакции. Это нужно
  учитывать при написании сервисов.
