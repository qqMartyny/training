# Как мы работаем

## Ветки

- `main` — то, что на проде.
- `release/x.y.z` — стабилизация релиза.
- `feature/SHOP-123-short-name`, `fix/SHOP-123-short-name` — рабочие ветки, PR в `release/*` или `main`.

## Коммиты

[Conventional Commits](https://www.conventionalcommits.org/ru/) + номер тикета:

```
fix(payment): SHOP-236 обрабатывать PENDING как ожидание оплаты
test(order): SHOP-256 тест переходов статусов проверяет все пары
refactor(pricing): SHOP-238 стратегии скидок вместо строковых типов
```

## Definition of Done

1. Корневая причина найдена и описана в PR.
2. Есть автотест, который падал до исправления.
3. `./mvnw clean verify` зелёный локально и в CI.
4. Публичный контракт (`openapi.yaml`, `asyncapi.yaml`) не нарушен. Если он меняется, изменение согласовано
   и документ обновлён.
5. Архитектурные изменения оформлены ADR.
6. Код прошёл ревью одного разработчика.

## Миграции БД

- Одна миграция = одно логическое изменение.
- **Применённую миграцию не редактировать.** Flyway хранит её контрольную сумму, и на stage и проде
  миграция уже выполнена. Нужно что-то поменять — пиши новую.
- Номер версии берётся при мерже, а не при создании ветки. Если в целевой ветке уже есть такой номер,
  перенумеруй свою миграцию.

## Тесты

| Тип | Суффикс | Запуск | Что можно |
|---|---|---|---|
| Юнит | `*Test` | `./mvnw test` | только JVM, моки |
| Slice | `*Test` | `./mvnw test` | `@WebMvcTest`, `@DataJpaTest` |
| Интеграционный | `*IT` | `./mvnw verify` | весь контекст + Testcontainers |

Каждый интеграционный тест работает со своими данными (новый `customerId`, новый товар).
Тесты не должны зависеть от порядка запуска.

## Код-стайл

- Конструкторная инъекция, поля `final`.
- DTO — `record`.
- Деньги — `BigDecimal`, сравнение через `compareTo`.
- Никаких `System.out`. Логирование через SLF4J без секретов и персональных данных.
